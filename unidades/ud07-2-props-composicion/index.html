    7.2. Props, Composición y Reutilización en React (RA4)

    Referencia Módulo DWEC: Resultado de Aprendizaje 4 (RA4) — Diseña aplicaciones web evaluando e integrando frameworks y librerías del entorno cliente para garantizar la modularidad, escalabilidad y mantenibilidad del software.

    7.2.1. Flujo Unidireccional de Datos (Top-Down Data Flow)

    En la arquitectura de React, la información viaja en una sola dirección: desde los componentes superiores (padres) hacia los componentes inferiores (hijos). Este paradigma se conoce como flujo de datos descendente o unidirectional data flow.

    State -->|1. Transmite Props| H1

    H1 -.->|2. Invoca Callback (onLogout)| State

    Principios Fundamentales del Flujo Descendente:

    1. Población de Arriba a Abajo: Ningún componente hijo conoce el origen del estado que recibe como props; solo sabe que se le ha proporcionado un conjunto de valores para representar su vista.

    2. Propiedades de Solo Lectura: Las props son inmutables. Un componente hijo jamás debe modificar el objeto props recibido.

    3. Comunicación Ascendente Mediante Eventos: Si un componente hijo necesita solicitar un cambio en la interfaz, lo hace invocando una función callback transmitida previamente por el padre como prop.

    7.2.2. Definición y Tipado Estático de Props con TypeScript

    El uso de TypeScript junto con React permite validar estáticamente la interfaz de comunicación de los componentes durante el tiempo de compilación, eliminando errores en tiempo de ejecución por propiedades ausentes o con tipos incompatibles.

    7.2.2.1. Interfaces frente a Tipos Alias

    Para definir el contrato de props de un componente se pueden utilizar tanto interface como type. En proyectos empresariales con React se recomienda el uso de interface para definir objetos de propiedades por su capacidad de extensión.

    import React from 'react';

// 1. Definición de la interfaz de Props
export interface TarjetaProductoProps {
  id: string;
  nombre: string;
  precio: number;
  disponible?: boolean; // Propiedad opcional
  etiquetas: string[];
  categoria: 'electronica' | 'ropa' | 'hogar'; // Unión de literales
  onAgregarCarrito: (id: string) => void; // Función Callback
}

// 2. Componente con tipado explícito mediante React.FC o parámetros directos
export const TarjetaProducto: React.FC<TarjetaProductoProps> = ({
  id,
  nombre,
  precio,
  disponible = true, // Valor por defecto mediante default assignment
  etiquetas,
  categoria,
  onAgregarCarrito
}) => {
  return (
    <article className={`tarjeta ${!disponible ? 'agotado' : ''}`}>
      <span className="categoria">{categoria.toUpperCase()}</span>
      <h3>{nombre}</h3>
      <p className="precio">${precio.toFixed(2)}</p>

      <div className="etiquetas">
        {etiquetas.map((tag, idx) => (
          <span key={idx} className="tag">{tag}</span>
        ))}
      </div>

      <button 
        disabled={!disponible}
        onClick={() => onAgregarCarrito(id)}
      >
        {disponible ? 'Añadir al Carrito' : 'Agotado'}
      </button>
    </article>
  );
};

    7.2.3. La Prop Especial children y la Proyección de Contenido

    React reserva una propiedad especial denominada children para transmitir componentes, elementos JSX o cadenas de texto en el espacio de apertura y cierre de un componente (<Componente>...</Componente>).

    Tipado de children en TypeScript

    El tipo oficial proporcionado por @types/react para children es React.ReactNode, el cual engloba elementos JSX, cadenas, números, arrays de JSX, fragmentos o valores booleanos/nulos.

    import React, { ReactNode } from 'react';

interface TarjetaContenedoraProps {
  titulo: string;
  children: ReactNode; // Permite cualquier contenido JSX válido
}

export const TarjetaContenedora: React.FC<TarjetaContenedoraProps> = ({ titulo, children }) => {
  return (
    <div className="tarjeta-shell">
      <header className="tarjeta-header">
        <h2>{titulo}</h2>
      </header>
      <main className="tarjeta-body">
        {children} {/* Proyección dinámica de contenido */}
      </main>
    </div>
  );
};

    Uso con proyección flexible:

    <TarjetaContenedora titulo="Perfil del Usuario">
  <img src="/avatar.jpg" alt="Usuario" />
  <p>Nombre: Ana Gómez</p>
  <button>Editar Perfil</button>
</TarjetaContenedora>

    7.2.4. Composición frente a Herencia en React

    A diferencia de los lenguajes POO tradicionales como Java o C++, React descarta la herencia de clases para extender componentes a favor del patrón de Composición de Software.

    Razones Técnicas del Rechazo a la Herencia:

    • Fragilidad de la Jerarquía: La herencia genera un acoplamiento rígido entre la clase base y las subclases.
    • Problema del Diamante: Dificultad para combinar funcionalidades independientes de múltiples ancestros.
    • Flexibilidad en Tiempo de Ejecución: La composición permite ensamblar comportamientos dinámicamente inyectando elementos mediante props o children.

    Patrón de Especialización vía Composición:

    Un componente "especial" puede renderizar un componente más "genérico" configurándolo mediante props:

    import React, { ReactNode } from 'react';

// 1. Componente Genérico (Diálogo Base)
interface DialogoProps {
  titulo: string;
  mensaje: string;
  children?: ReactNode; // Slot para botones o controles adicionales
}

export const Dialogo: React.FC<DialogoProps> = ({ titulo, mensaje, children }) => (
  <div className="dialogo-overlay">
    <div className="dialogo-box">
      <h3>{titulo}</h3>
      <p>{mensaje}</p>
      {children && <footer className="dialogo-acciones">{children}</footer>}
    </div>
  </div>
);

// 2. Componente Especializado vía Composición
export const DialogoConfirmacionBorrado: React.FC<{ onConfirmar: () => void }> = ({ onConfirmar }) => (
  <Dialogo
    titulo="¿Confirmar eliminación?"
    mensaje="Esta acción no se puede deshacer. Los datos serán destruidos permanentemente."
  >
    <button className="btn-cancelar">Cancelar</button>
    <button className="btn-peligro" onClick={onConfirmar}>
      Sí, Eliminar
    </button>
  </Dialogo>
);

    7.2.5. Patrones de Reutilización: Componentes Contenedores vs Presentacionales y Layouts

    7.2.5.1. Separación de Responsabilidades: Container & Presentational Pattern

    Aunque los Hooks modernos simplifican la cohesión de lógica y vista, la separación entre la capa de datos/lógica y la capa visual sigue siendo clave para el mantenimiento:

    Criterio Componente Presentacional ("Dumb") Componente Contenedor ("Smart")
    Responsabilidad Cómo se ven las cosas en pantalla (UI).

    | Cómo funcionan las cosas (Datos / Lógica).

    | | Acceso a APIs | Ninguno. Solo usa props.

    | Directo (fetch, useEffect, llamadas a servicios).

    | | Estado Interno | Solo estado visual local (ej. dropdown abierto).

    | Estado de datos de negocio (listados, errores).

    | | Reutilización | Muy alta en múltiples contextos del diseño.

    | Baja, atado a un dominio de negocio específico.

    |

    7.2.5.2. Componentes de Layout (Estructura Base)

    Los componentes de Layout organizan la estructura general de la vista (header, sidebar, footer) evitando duplicar maquetación en las páginas de la aplicación:

    import React, { ReactNode } from 'react';

interface MainLayoutProps {
  sidebarContent: ReactNode;
  children: ReactNode;
}

export const MainLayout: React.FC<MainLayoutProps> = ({ sidebarContent, children }) => {
  return (
    <div className="app-grid-layout">
      <header className="app-header">
        <h1>Sistema de Gestión DWEC</h1>
      </header>
      <aside className="app-sidebar">{sidebarContent}</aside>
      <main className="app-content">{children}</main>
      <footer className="app-footer">© 2026 - IES Puerto de la Cruz</footer>
    </div>
  );
};

    7.2.6. Inmutabilidad de Props, Desestructuración y Buenas Prácticas

    1. Inmutabilidad Estricta

    Las props son enviadas congeladas conceptualmente. Si un componente necesita alterar un valor recibido como prop, debe solicitar al padre la actualización invocando un callback.

    // ❌ MAL: Intento de mutación de props
const ContadorIncorrecto = (props: { total: number }) => {
  props.total = props.total + 1; // Error en modo estricto de TypeScript
  return <span>{props.total}</span>;
};

// Custom Hook / Callback (FORMA CORRECTA)
const ContadorCorrecto = ({ total, onIncrementar }: { total: number; onIncrementar: () => void }) => (
  <button onClick={onIncrementar}>Total: {total}</button>
);

    2. Desestructuración Limpia con Valores por Defecto

    Desestructurar los parámetros de la función directamente en la firma del componente mejora la legibilidad y permite definir fallback values de forma idiomática:

    // Desestructuración limpia y directa en la firma
export const Alerta: React.FC<{ mensaje: string; tipo?: 'info' | 'error' }> = ({
  mensaje,
  tipo = 'info' // Valor por defecto
}) => (
  <div className={`alerta alerta-${tipo}`}>
    <p>{mensaje}</p>
  </div>
);

    7.2.7. Resumen de Conceptos Clave del apartado 7.2

    Concepto Descripción Técnica Garantía Arquitectónica (RA4)
    Top-Down Flow Los datos fluyen de forma unidireccional de padres a hijos.

    | Predecibilidad y aislamiento de fallos de renderizado.

    | | TypeScript Props | Tipado estático mediante interface o type en componentes React.

    | Prevención de errores por datos ausentes o mal formateados en desarrollo.

    | | React.ReactNode | Tipo genérico para la prop especial children.

    | Permite la composición de vistas y la inyección flexible de elementos JSX.

    | | Composición | Construcción de interfaces complejas mediante la combinación de componentes simples.

    | Reemplaza la herencia, garantizando un código modular y escalable.

    | | Smart / Dumb | Separación entre lógica de datos (Smart) y renderizado UI (Dumb).

    | Alta reutilización de componentes UI y código más testeable.

    |
