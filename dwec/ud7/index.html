    UD 7: Introducción Histórica, Evolución y Fundamentos de la Arquitectura Frontend

    Referencia Módulo DWEC: Resultado de Aprendizaje 4 (RA4) — Diseña aplicaciones web evaluando e integrando frameworks y librerías del entorno cliente para garantizar la modularidad, escalabilidad y mantenibilidad del software.

    1. Historia y Evolución del Desarrollo Web Client-Side

    Para entender la arquitectura de los frameworks modernos (React, Angular, Vue, Svelte, Qwik), es necesario analizar la evolución histórica de las necesidades técnicas que surgieron al transformar la Web desde un sistema de distribución de documentos estáticos hacia una plataforma de ejecución de aplicaciones de software distribuido en tiempo real.

    graph TD
    A["<b>1. Era del Documento Estático (1990 - 2004)</b><br>HTML / CSS / PHP / CGI<br>Arquitectura MPA y Recargas Completas de Página"] --> B["<b>2. Era de la Interactividad y AJAX (2005 - 2010)</b><br>XMLHttpRequest / DHTML / jQuery<br>Inyección Asíncrona y Parches al DOM Real"]
    B --> C["<b>3. Primera Gen SPA / MV* (2010 - 2013)</b><br>Backbone.js / Knockout.js / AngularJS<br>Data-Binding Bidireccional y Digest Loops"]
    C --> D["<b>4. Era Componentes y Virtual DOM (2013 - 2019)</b><br>React / Vue / Angular 2+<br>Flujo Unidireccional, VDOM y JSX/Templates"]
    D --> E["<b>5. Era de Compiladores y Reactividad Fina (2019 - Presente)</b><br>Svelte / SolidJS / Qwik / Astro / Next.js<br>Sin VDOM, Reanudabilidad (Resumability) y SSR/SSG"]

    1.1. La Era del Documento Estático y CGI/PHP (1990 - 2004)

    En los orígenes de la World Wide Web, el navegador era exclusivamente un cliente de visualización de documentos hipertexto. La arquitectura dominante era MPA (Multi-Page Application):

    1. El usuario solicitaba una URL o enviaba un formulario HTML (<form action="/procesar" method="POST">).

    2. El servidor web (utilizando scripts CGI en Perl, PHP, ASP o Java Servlets) procesaba la lógica de negocio, realizaba consultas a la base de datos SQL y generaba un nuevo archivo HTML completo en el servidor.

    3. El servidor enviaba la cadena HTML resultante a través de HTTP.

    4. El navegador descartaba por completo el árbol DOM anterior, limpiaba la memoria RAM y procesaba el nuevo HTML desde cero (provocando el característico "parpadeo blanco" de pantalla).

    sequenceDiagram
    autonumber
    actor Cliente as Cliente (Navegador)
    participant Servidor as Servidor Web (PHP / SQL)

    Cliente->>Servidor: 1. Petición HTTP (GET / POST)
    Note over Servidor: Procesa datos y genera HTML estático
    Servidor-->>Cliente: 2. Devuelve archivo HTML Completo
    Note over Cliente: Limpia memoria RAM y vuelve a pintar la pantalla

    JavaScript (creado por Brendan Eich en Netscape en 1995) se utilizaba de forma marginal para tareas cosméticas sencillas (validaciones básicas de campos de texto antes del envío, efectos visuales con DHTML o marquesinas de texto).

    1.2. La Revolución AJAX y la Era de jQuery (2005 - 2010)

    En marzo de 2005, Jesse James Garrett acuñó el término AJAX (Asynchronous JavaScript and XML), un hito tecnológico fundamentado en el objeto XMLHttpRequest (creado originalmente por Microsoft para Internet Explorer 5.0 en 1999).

    AJAX permitió romper el paradigma de la recarga total de página: el JavaScript que se ejecutaba en el cliente podía realizar peticiones de datos HTTP en segundo plano y actualizar áreas específicas del DOM dinámicamente. Aplicaciones emblemáticas como Google Maps (2005) y Gmail demostraron que la Web podía ofrecer una experiencia fluida equivalente a las aplicaciones nativas de escritorio.

    Sin embargo, surgió una gran problemática: la fragmentación de los navegadores. Las APIs del DOM y la implementación de XMLHttpRequest diferían sustancialmente entre Internet Explorer 6, Firefox, Safari y Opera.

    En 2006, John Resig lanzó jQuery, una librería que resolvió la incompatibilidad multiplataforma abstraendo el DOM nativo tras una sintaxis unificada:

    // Manipulación imperativa con jQuery (2006)
$("#btn-cargar-usuario").click(function() {
  $.ajax({
    url: "/api/usuario/10",
    method: "GET",
    success: function(data) {
      // Inyección manual e imperativa en el DOM Real
      $("#nombre").text(data.nombre);
      $("#avatar").attr("src", data.foto);
      $("#estado").removeClass("offline").addClass("online");
    },
    error: function(err) {
      alert("Error al cargar usuario");
    }
  });
});

    El problema del "Spaghetti Code" en jQuery

    :

    A medida que la complejidad de las interfaces creció, jQuery demostró ser insostenible para aplicaciones a gran escala:

    • Sin separación de responsabilidades: La lógica de negocio, la lectura de datos del DOM y la modificación visual estaban mezcladas en los mismos ficheros.

    • Estado acoplado al DOM: El estado de la aplicación se almacenaba en el propio HTML (atributos data-*, clases CSS o texto de los elementos). Para leer el valor actual de un formulario, había que consultar el DOM Real.

    • Complejidad Combinatoria: Si $N$ eventos podían modificar $M$ elementos visuales, el desarrollador debía escribir y mantener $N \times M$ mutaciones manuales.

    1.3. La Primera Generación de Frameworks SPA: El Patrón MVVM (2010 - 2013)

    Para solucionar el descontrol organizativo de jQuery, surgieron los primeros frameworks diseñados para crear SPAs (Single-Page Applications) aplicando patrones de arquitectura clásicos como MVC (Modelo-Vista-Controlador) o MVVM (Modelo-Vista-VistaModelo):

    • Backbone.js (2010): Aportó estructura mediante Models, Collections y Views, integrando un enrutador en el cliente basándose en el fragmento hash de la URL (#).

    • Knockout.js (2010): Introdujo el concepto de observables y la vinculación declarativa de datos.

    • AngularJS (2010, Google): Dominó la industria introduciendo el Data-Binding Bidireccional (Two-Way Data Binding), la Inyección de Dependencias y las Directivas personalizadas HTML.

    Data-Binding Bidireccional (AngularJS / MVVM):
   ┌──────────────┐   Sincronización Automática   ┌──────────────┐
   │ Modelo (JS)  │ <===========================> │ Vista (DOM)  │
   └──────────────┘                               └──────────────┘

    El colapso del Data-Binding Bidireccional y el "Digest Loop"

    En AngularJS, cuando un valor cambiaba en la vista (por ejemplo, mediante un <input ng-model="usuario.nombre">), el marco desencadenaba un ciclo de inspección sucia denominado Digest Loop ($digest cycle):

    1. AngularJS evaluaba todos los vigilantes ($watchers) registrados en la aplicación para comprobar qué variables del ámbito ($scope) habían mutado.

    2. Si un watcher modificaba otro modelo, el ciclo debía ejecutarse de nuevo para verificar los impactos derivados (hasta un máximo de 10 iteraciones de seguridad).

    3. En aplicaciones empresariales con miles de watchers activos, el tiempo de procesamiento en el hilo principal (Main Thread) superaba los 16.6ms (el límite para mantener 60 FPS), provocando bloqueos constantes en la interfaz.

    1.4. La Revolución de los Componentes y el Virtual DOM (2013 - 2019)

    A principios de la década de 2010, los ingenieros de Facebook (Meta) se enfrentaron a un reto crítico en su interfaz web: la complejidad del News Feed y del chat. La sincronización del estado de la aplicación mediante patrones imperativos o los modelos MV* de la época resultaba inmanejable.

    Para resolver esta problemática, Jordan Walke, ingeniero de software en Facebook, creó en 2011 un prototipo llamado FaxJS, que posteriormente evolucionó en React. Se probó en el News Feed en 2011, en Instagram en 2012 y en mayo de 2013 se liberó como código abierto durante la conferencia JSConf US.

    React rompió con las convenciones vigentes estableciendo tres pilares revolucionarios:

    1. Flujo Unidireccional de Datos (One-Way Data Flow): El estado fluye exclusivamente de padres a hijos. Se eliminaron las actualizaciones cruzadas e impredecibles del Data-Binding bidireccional.

    2. Virtual DOM (VDOM): En lugar de manipular el DOM Real directamente, React genera una copia ligera en memoria RAM y utiliza un algoritmo de diferenciación (Diffing) para aplicar únicamente las modificaciones estrictamente necesarias.

    3. Cohesión vía Componentes y JSX: Se descartó la separación clásica de tecnologías (fichero .html, fichero .js, fichero .css) a favor de la separación por responsabilidades funcionales mediante componentes que encapsulan la lógica y la representación visual utilizando JSX (JavaScript XML).

    // React Component (2013)
function TarjetaUsuario({ usuario }) {
  return (
    <div className="card">
      <img src={usuario.foto} alt={usuario.nombre} />
      <h3>{usuario.nombre}</h3>
    </div>
  );
}

    El éxito de React obligó al resto de la industria a evolucionar:

    • Google abandonó AngularJS por completo y reescribió el marco desde cero en TypeScript: Angular 2+ (2016), adoptando una arquitectura orientada a componentes.

    • Vue.js (2014, Evan You) combinó la simplicidad sintáctica de las plantillas de AngularJS con la potencia del Virtual DOM y el flujo unidireccional de React.

    1.5. La Tercera Generación: Compilación y Reactividad Fina (2019 - Presente)

    Aunque el Virtual DOM resolvió los cuellos de botella de la manipulación masiva del DOM, introduce una sobrecarga computacional inherente: con cada cambio de estado, hay que instanciar objetos JS, comparar árboles en memoria y ejecutar recolecciones de basura (Garbage Collection).

    Los marcos modernos han prescindido del Virtual DOM mediante diferentes estrategias:

    graph LR
    subgraph VDOM["Enfoque Basado en Virtual DOM (React / Vue)"]
        A1["Estado Cambia"] --> A2["Ejecutar Función de Componente"]
        A2 --> A3["Crear Nuevo Árbol VDOM"]
        A3 --> A4["Algoritmo Diffing (Comparar Árboles)"]
        A4 --> A5["Parchear DOM Real"]
    end

    subgraph Compiler["Enfoque Compilado / Reactividad Fina (Svelte / SolidJS)"]
        B1["Estado Cambia"] --> B2["Llamada Directa al Nodo del DOM"]
        B2 --> B3["Actualización Quirúrgica del DOM Real"]
    end

    • Svelte (Rich Harris, 2019): Traslada el trabajo del navegador al tiempo de compilación. Svelte no utiliza runtime ni Virtual DOM; su compilador transforma los componentes .svelte en código JavaScript Vanilla altamente optimizado que actualiza directamente los nodos del DOM Real al detectar cambios.

    • SolidJS (Ryan Carniato, 2021): Utiliza la sintaxis JSX de React pero sin Virtual DOM. Emplea un sistema de reactividad fina (Fine-Grained Reactivity) mediante Señales (Signals). La función del componente se ejecuta una sola vez al montarse; posteriormente, las señales se suscriben directamente a los nodos específicos del DOM.

    • Qwik (Misko Hevery, 2022): Introduce el concepto de Reanudabilidad (Resumability). Cancela el proceso de hidratación enviando el estado de la aplicación serializado dentro del propio HTML, permitiendo una interactividad instantánea ($TTI \approx 0\text{ ms}$) descargando $0\text{ kB}$ de JavaScript inicial.

    2. El Problema Técnico de la Manipulación Directa del DOM Real

    Para entender el propósito fundamental de un framework frontend moderno, se debe analizar la arquitectura interna del motor de renderizado de un navegador web (ej. Blink en Chromium, Gecko en Firefox, WebKit en Safari).

    2.1. Anatomía del DOM Real

    El DOM (Document Object Model) es una interfaz de programación (API) que representa el documento HTML como un árbol de nodos en C++. Cada elemento HTML (ej. <div>, <p>) es una instancia de una clase C++ pesada dentro del proceso del navegador (HTMLDivElement, HTMLParagraphElement).

    El coste de interactuar con el DOM no reside en ejecutar código JavaScript, sino en la comunicación cruzada entre el motor de JS (V8) y el motor de renderizado (Blink) mediante bindings de C++, sumado a la ejecución del flujo de renderizado del navegador (Critical Rendering Path).

    2.2. La Tubería de Renderizado del Navegador (Rendering Pipeline)

    Cada vez que JavaScript modifica una propiedad geométrica del DOM Real (como width, height, margin, o inserta un nodo hijo), el navegador debe ejecutar una secuencia de cómputo pesada:

    flowchart TD
    JS["1. JavaScript Execution<br>(Modificación de nodos o estilos)"] --> Recalc["2. Style Recalculation<br>(Cálculo de reglas CSS aplicables a cada nodo)"]
    Recalc --> Layout["3. Layout / Reflow<br>(Cálculo de posiciones X, Y, ancho y alto de cada elemento)"]
    Layout --> Paint["4. Paint / Rasterization<br>(Rellenar píxeles en capas de mapa de bits)"]
    Paint --> Composite["5. Compositing<br>(Ensamblado de capas en la GPU para el monitor)"]

    1. Recalculate Style: Determina qué reglas CSS atañen a cada elemento del árbol en función de los selectores aplicados.

    2. Layout (Reflow): Proceso computacional crítico. El navegador calcula la geometría exacta (coordenadas cartesianas y dimensiones en píxeles) de todos los elementos de la página. Un cambio diminuto en el ancho de un contenedor superior puede forzar el re-cálculo geométrico del 100% del árbol de la pantalla.

    3. Paint: Pinta texturas, textos, bordes y sombras en capas de mapas de bits (Bitmaps).

    4. Composite: La GPU (Graphics Processing Unit) toma las capas generadas y las ensambla en la pantalla.

    2.3. El Fenómeno del Layout Thrashing (Sobrecarga de Layout)

    Un error común en el desarrollo con Vanilla JS o jQuery es intercalar operaciones de escritura y lectura sobre el DOM en el mismo bucle de ejecución:

    // ❌ CÓDIGO INEFICIENTE: Provoca Layout Thrashing
const elementos = document.querySelectorAll(".caja");

for (let i = 0; i < elementos.length; i++) {
  // 1. LECTURA: Fuerza al navegador a ejecutar un Reflow sincrónico e inmediato
  const alto = elementos[i].offsetHeight;

  // 2. ESCRITURA: Invalida el layout actual
  elementos[i].style.height = (alto + 10) + "px";
}

    En este escenario, el navegador se ve obligado a pausar la ejecución de JS e invocar el algoritmo de Layout repetidamente en cada iteración del bucle, degradando la tasa de refresco por debajo de los 60 cuadros por segundo (causando congelamientos visuales o Lag/Jank).

    3. Paradigmas de Programación Frontend: Imperativo vs. Declarativo

    El desarrollo de interfaces de usuario ha experimentado una transición paradigmática desde el enfoque imperativo hacia el modelo declarativo basado en estado.

    graph TD
    subgraph Imperativo["Paradigma Imperativo (Vanilla JS / jQuery)"]
        I1["Evento del Usuario"] --> I2["Buscar Nodo A en el DOM"]
        I2 --> I3["Modificar Atributo en Nodo A"]
        I3 --> I4["Buscar Nodo B en el DOM"]
        I4 --> I5["Modificar Clase CSS en Nodo B"]
    end

    subgraph Declarativo["Paradigma Declarativo (React / Vue / Svelte)"]
        D1["Evento del Usuario"] --> D2["Actualizar Estado de la App"]
        D2 --> D3["Framework Detecta Cambio de Estado"]
        D3 --> D4["UI se Sincroniza Automáticamente: UI = f(Estado)"]
    end

    3.1. Paradigma Imperativo (Cómo debe hacerse)

    El desarrollador especifica paso a paso la secuencia de instrucciones necesaria para pasar la interfaz de un estado $A$ a un estado $B$.

    • Pregunta clave: "¿CÓMO modifico la pantalla elemento a elemento?"

    • Inconveniente principal: A medida que la interfaz suma más elementos interactivos, el número de estados posibles de la UI crece de forma exponencial. Si el programador olvida actualizar manualmente un nodo en alguno de los caminos condicionales del código, la pantalla mostrará datos inconsistentes.

    3.2. Paradigma Declarativo (Qué debe mostrarse)

    El desarrollador describe cómo debe verse la interfaz para un estado de datos determinado, desentendiéndose por completo del proceso mecánico de manipulación del DOM.

    • Pregunta clave: "¿QUÉ vista debe representarse para este estado de datos?"

    • Ecuación Fundamental del Frontend Declarativo:

    $$\text{UI} = f(\text{State})$$

    Donde $\text{State}$ representa el conjunto de datos de la aplicación en un instante de tiempo, $f$ es el conjunto de componentes y $\text{UI}$ es la interfaz proyectada.

    3.3. Comparativa Técnica Directa: Contador de Clics

    Código Imperativo (Vanilla JavaScript)

    // El desarrollador gestiona manualmente el estado y las mutaciones del DOM
let contador = 0;

const contadorTexto = document.createElement('p');
const boton = document.createElement('button');

contadorTexto.textContent = `Total clics: ${contador}`;
boton.textContent = 'Incrementar';

boton.addEventListener('click', () => {
  contador++; // 1. Mutar estado
  contadorTexto.textContent = `Total clics: ${contador}`; // 2. Mutar manualmente el DOM
});

document.body.appendChild(contadorTexto);
document.body.appendChild(boton);

    Código Declarativo (React)

    import { useState } from 'react';

// El desarrollador declara la relación entre el estado y la interfaz
function Contador() {
  const [contador, setContador] = useState(0);

  return (
    <div>
      <p>Total clics: {contador}</p>
      <button onClick={() => setContador(contador + 1)}>
        Incrementar
      </button>
    </div>
  );
}

    5. Estrategias Modernas de Renderizado, Despliegue e Hidratación

    La evolución de las necesidades de negocio (velocidad de carga, rendimiento en dispositivos móviles y SEO) ha dado lugar a múltiples arquitecturas de renderizado.

    flowchart TD
    A["Estrategias de Renderizado"] --> CSR["CSR<br>Client-Side Rendering"]
    A --> SSR["SSR<br>Server-Side Rendering"]
    A --> SSG["SSG<br>Static Site Generation"]
    A --> ISR["ISR<br>Incremental Static Regeneration"]

    5.1. Client-Side Rendering (CSR)

    Es el modelo clásico de las aplicaciones SPA compiladas con herramientas como Vite o Create React App.

    1. El navegador descarga un archivo index.html prácticamente vacío con la etiqueta <div id="root"></div>.

    2. El navegador descarga y ejecuta el archivo JavaScript del bundle.

    3. El JavaScript realiza las peticiones fetch() a las APIs externas.

    4. Una vez obtenidos los datos, JavaScript monta los componentes en el DOM.

    5.2. Server-Side Rendering (SSR)

    Implementado por meta-frameworks como Next.js (React), Nuxt (Vue) o SvelteKit.

    1. El usuario realiza una petición HTTP al servidor Node.js/Edge.

    2. El servidor procesa los componentes y realiza las consultas de datos en tiempo de ejecución.

    3. El servidor renderiza los componentes a HTML puro y los envía al navegador.

    4. El navegador pinta el HTML de inmediato (FCP veloz y SEO óptimo) y ejecuta el proceso de Hidratación.

    5.3. Static Site Generation (SSG) e Incremental Static Regeneration (ISR)

    • SSG: Los archivos HTML, CSS y JS se renderizan una sola vez durante la fase de compilación/construcción (npm run build) y se sirven mediante CDNs con máxima velocidad ($TTFB$ muy bajo).

    • ISR: Permite definir un tiempo de revalidación (ej. revalidate: 60 s) para regenerar páginas estáticas en segundo plano a medida que entran nuevas peticiones sin reconstruir todo el sitio web.

    5.4. El Proceso de Hidratación (Hydration)

    La Hidratación es la técnica arquitectónica mediante la cual JavaScript "cobra vida" sobre un documento HTML generado previamente por el servidor (SSR/SSG).

    Término / Concepto Descripción Técnica Función Principal en la Arquitectura
    Imperativo Programación mediante instrucciones secuenciales directas sobre el DOM.

    | Típico de Vanilla JS/jQuery. Difícil de escalar.

    | | Declarativo | Describir el estado final deseado de la UI ($\text{UI} = f(\text{State})$).

    | Paradigma central de los frameworks modernos.

    | | SPA | Single Page Application. Aplicación web cargada en una sola página.

    | Evita recargas de página completas mediante CSR.

    | | MPA | Multi-Page Application. Aplicación con recargas tradicionales.
