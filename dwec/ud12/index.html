    UD 12: Context API y Estado Global (RA6)

    Referencia Módulo DWEC: Resultado de Aprendizaje 6 (RA6) — Optimiza el rendimiento de aplicaciones web en el entorno cliente gestionando el estado de la aplicación mediante mecanismos que evitan el acoplamiento excesivo entre componentes y el paso manual de datos a través de múltiples niveles del árbol de componentes.

    1. El Problema: Prop Drilling

    A medida que una aplicación React crece en profundidad de componentes, es habitual necesitar un mismo dato (el usuario autenticado, el tema visual, el idioma) en componentes muy alejados del componente que originalmente lo obtiene.

    La solución "ingenua" consiste en pasar ese dato como prop de padre a hijo en cada nivel, aunque los componentes intermedios no lo necesiten para nada propio. Este antipatrón se conoce como Prop Drilling (perforación de props).

    flowchart TD
    App["App (tiene el usuario)"] -->|prop: usuario| Layout
    Layout -->|prop: usuario| Sidebar
    Sidebar -->|prop: usuario| Menu
    Menu -->|prop: usuario| Avatar["Avatar (el único que realmente lo usa)"]
    • Consecuencias: componentes intermedios acoplados a datos que no usan, refactorizaciones costosas (cambiar el nombre de una prop obliga a tocar toda la cadena) y una API de componentes cada vez más ruidosa.
    • Cuándo NO es un problema: si el dato solo baja 1 o 2 niveles, pasar la prop directamente sigue siendo la solución más simple y explícita. Context API no sustituye el paso de props locales; resuelve específicamente la comunicación entre partes distantes del árbol.

    2. Context API: createContext y useContext

    React ofrece un mecanismo nativo para crear un "canal" de datos que cualquier componente descendiente puede leer directamente, sin que los intermedios tengan que reenviarlo.

    flowchart TD
    Provider["ThemeContext.Provider (value={tema})"] --> A[Layout]
    A --> B[Sidebar]
    A --> C[Contenido]
    C --> D["Boton (usa useContext directamente)"]
    Provider -.->|"lectura directa, sin pasar por A, B o C"| D

    2.1. Creación del contexto

    // contexts/ThemeContext.js
import { createContext, useState, useContext } from 'react';

// 1. Se crea el "canal". El valor por defecto solo se usa si no hay Provider por encima.
const ThemeContext = createContext(null);

// 2. Componente Provider: envuelve la parte del árbol que necesita acceso al dato
export function ThemeProvider({ children }) {
  const [tema, setTema] = useState('claro');

  const alternarTema = () => {
    setTema(actual => (actual === 'claro' ? 'oscuro' : 'claro'));
  };

  // El "value" es lo que estará disponible para cualquier descendiente
  const valor = { tema, alternarTema };

  return (
    <ThemeContext.Provider value={valor}>
      {children}
    </ThemeContext.Provider>
  );
}

// 3. Custom Hook de conveniencia (patrón recomendado, ver apartado 2.3)
export function useTheme() {
  const contexto = useContext(ThemeContext);
  if (contexto === null) {
    throw new Error('useTheme debe usarse dentro de un ThemeProvider');
  }
  return contexto;
}

    2.2. Consumo del contexto

    Cualquier componente, sin importar su profundidad, puede leer el valor con useContext:

    // components/Boton.jsx
import { useTheme } from '../contexts/ThemeContext';

function Boton() {
  const { tema, alternarTema } = useTheme();

  return (
    <button
      onClick={alternarTema}
      className={tema === 'oscuro' ? 'btn-dark' : 'btn-light'}
    >
      Tema actual: {tema}
    </button>
  );
}

    // App.jsx
import { ThemeProvider } from './contexts/ThemeContext';

function App() {
  return (
    <ThemeProvider>
      <Layout />
    </ThemeProvider>
  );
}

    2.3. Patrón recomendado: Custom Hook + validación

    Consumir el contexto siempre a través de un hook propio (useTheme, useAuth, useCarrito...) en lugar de llamar a useContext(ThemeContext) directamente en cada componente aporta dos ventajas:

    • Encapsulación: si el día de mañana cambia la implementación interna (por ejemplo, se sustituye por Zustand), solo hay que tocar el hook, no cada componente consumidor.
    • Seguridad: lanzar un error explícito si el hook se usa fuera de su Provider evita bugs silenciosos (recibir null y no saber por qué).

    3. Múltiples Contextos y Composición de Providers

    Es habitual que una aplicación necesite varios contextos independientes (autenticación, tema, carrito de compra). Cada uno se declara y se compone por separado, anidando los Provider en la raíz:

    function App() {
  return (
    <AuthProvider>
      <ThemeProvider>
        <CarritoProvider>
          <Layout />
        </CarritoProvider>
      </ThemeProvider>
    </AuthProvider>
  );
}

    Buena práctica: mantener cada contexto centrado en una única responsabilidad (Single Responsibility). Un contexto "todo en uno" con usuario, tema, carrito y notificaciones mezcladas es difícil de mantener y, como se ve en el apartado 4, provoca renderizados innecesarios.

    4. El Problema de Rendimiento: Re-renderizados en Cascada

    Context API no está optimizada para valores que cambian con mucha frecuencia. Cuando el value de un Provider cambia, todos los componentes que consumen ese contexto con useContext se vuelven a renderizar, independientemente de si usan la parte del valor que cambió.

    flowchart TD
    Provider["Provider value cambia"] --> C1["Componente A (usa 'usuario')"]
    Provider --> C2["Componente B (usa 'tema')"]
    Provider --> C3["Componente C (usa 'notificaciones')"]

    note1["Si 'notificaciones' cambia,<br/>A y B también se re-renderizan<br/>aunque no usen ese dato"]

    4.1. Mitigaciones

    • Dividir contextos por dominio y por frecuencia de cambio: separar un valor que cambia constantemente (por ejemplo, la posición del ratón) de otro estable (el usuario autenticado) en contextos distintos.
    • Memorizar el value del Provider con useMemo para evitar crear un objeto nuevo en cada render del componente Provider:
    function CarritoProvider({ children }) {
  const [items, setItems] = useState([]);

  // Sin useMemo, cada render de CarritoProvider crea un objeto "valor" nuevo,
  // lo que fuerza el re-render de TODOS los consumidores aunque items no cambie.
  const valor = useMemo(() => ({ items, setItems }), [items]);

  return <CarritoContext.Provider value={valor}>{children}</CarritoContext.Provider>;
}
    • Separar estado y acciones en dos contextos cuando el patrón lo justifique: un contexto para los datos (que cambia) y otro para las funciones que los modifican (que no cambian nunca su referencia si se envuelven en useCallback), de modo que los componentes que solo disparan acciones no se re-rendericen cuando cambian los datos.

    5. Context API vs. Librerías de Estado Global (Zustand / Redux)

    Context API es la solución nativa de React, pero no es la única ni siempre la más adecuada. Es fundamental saber razonar cuándo conviene cada opción.

    Criterio Context API (nativo) Zustand / Redux (librería externa)
    Instalación Ninguna, viene con React Requiere añadir una dependencia (npm install zustand)
    Rendimiento con cambios frecuentes Deficiente sin optimización manual (re-renderiza todos los consumidores) Optimizado por defecto: los componentes solo se suscriben a la porción de estado que usan
    Curva de aprendizaje Muy baja (2 funciones: createContext, useContext) Baja (Zustand) a media (Redux, con actions, reducers, middleware)
    Herramientas de depuración Ninguna específica DevTools dedicadas (historial de acciones, time-travel debugging en Redux)
    Caso de uso ideal Estado que cambia poco: tema visual, idioma, datos de sesión del usuario, preferencias Estado complejo y muy dinámico: carritos con muchas operaciones, filtros de listados grandes, estado compartido entre módulos independientes

    5.1. Ejemplo equivalente en Zustand (para contraste)

    // store/useCarritoStore.js
import { create } from 'zustand';

export const useCarritoStore = create((set) => ({
  items: [],
  añadir: (producto) =>
    set((estado) => ({ items: [...estado.items, producto] })),
  vaciar: () => set({ items: [] }),
}));

    // Cualquier componente, SIN Provider envolviendo la aplicación
function ContadorCarrito() {
  // Solo se re-renderiza si "items" cambia, no si cambia cualquier otra
  // parte del store que pueda existir en el futuro
  const totalItems = useCarritoStore((estado) => estado.items.length);
  return <span>{totalItems} artículos</span>;
}

    La diferencia clave es la suscripción selectiva: en Zustand, cada componente elige exactamente qué "trozo" del estado le interesa mediante una función selector, y solo se re-renderiza si ese trozo concreto cambia. Context API, sin trabajo adicional, no ofrece esa granularidad.

    💡 Criterio práctico para el aula: para el estado típico de las prácticas de este módulo (usuario autenticado, tema, idioma) Context API es más que suficiente y evita una dependencia externa. Zustand se reserva para cuando el estado global gana en volumen y frecuencia de cambio (por ejemplo, un dashboard con múltiples widgets sincronizados).

    6. Caso Práctico Integrado: Carrito de Compra con Context API

    Ejemplo completo que combina createContext, useContext, useReducer (para centralizar la lógica de actualización) y el patrón de custom hook:

    // contexts/CarritoContext.jsx
import { createContext, useContext, useReducer } from 'react';

const CarritoContext = createContext(null);

function carritoReducer(estado, accion) {
  switch (accion.type) {
    case 'AÑADIR':
      return { ...estado, items: [...estado.items, accion.payload] };
    case 'ELIMINAR':
      return {
        ...estado,
        items: estado.items.filter((item) => item.id !== accion.payload),
      };
    case 'VACIAR':
      return { ...estado, items: [] };
    default:
      return estado;
  }
}

export function CarritoProvider({ children }) {
  const [estado, dispatch] = useReducer(carritoReducer, { items: [] });

  const valor = {
    items: estado.items,
    total: estado.items.reduce((acc, item) => acc + item.precio, 0),
    añadir: (producto) => dispatch({ type: 'AÑADIR', payload: producto }),
    eliminar: (id) => dispatch({ type: 'ELIMINAR', payload: id }),
    vaciar: () => dispatch({ type: 'VACIAR' }),
  };

  return (
    <CarritoContext.Provider value={valor}>{children}</CarritoContext.Provider>
  );
}

export function useCarrito() {
  const contexto = useContext(CarritoContext);
  if (!contexto) throw new Error('useCarrito debe usarse dentro de CarritoProvider');
  return contexto;
}

    // components/ResumenCarrito.jsx
import { useCarrito } from '../contexts/CarritoContext';

function ResumenCarrito() {
  const { items, total, eliminar, vaciar } = useCarrito();

  return (
    <aside>
      <h3>Carrito ({items.length})</h3>
      <ul>
        {items.map((item) => (
          <li key={item.id}>
            {item.nombre} — {item.precio} €
            <button onClick={() => eliminar(item.id)}>Quitar</button>
          </li>
        ))}
      </ul>
      <p>Total: {total} €</p>
      <button onClick={vaciar}>Vaciar carrito</button>
    </aside>
  );
}

    Combinar useReducer con Context API es un patrón muy habitual: el Provider centraliza tanto el dato como la lógica que lo modifica, y los componentes consumidores solo invocan acciones (añadir, eliminar, vaciar) sin conocer los detalles internos de cómo se actualiza el estado.

    7. Resumen de Conceptos Clave de la UD 12

    Término / Concepto Descripción Técnica Función Principal
    Prop Drilling Paso manual de una prop a través de múltiples niveles de componentes que no la necesitan. Problema que Context API busca resolver.
    createContext Crea un objeto "canal" de datos compartido. Define el contexto y su valor por defecto.
    Provider Componente que envuelve una parte del árbol y expone un value. Hace disponible el dato a todos sus descendientes.
    useContext Hook que lee el valor del contexto más cercano en el árbol. Consumo del dato sin pasar por props intermedias.
    Custom Hook de contexto Función (useTheme, useAuth...) que envuelve useContext y valida su uso. Encapsula y protege el acceso al contexto.
    Re-render en cascada Todo consumidor de un contexto se re-renderiza cuando cambia su value, sin distinción de qué parte usa. Principal limitación de rendimiento de Context API.
    Zustand / Redux Librerías externas de gestión de estado global con suscripción selectiva. Alternativa recomendada para estado complejo y muy dinámico.
