    13.4 (Empresa): CI/CD Pipelines y Seguridad Web (XSS, CSP, Cookies)

    !!! abstract "Contexto FCT" Este contenido es idéntico al de Material adicional: CI/CD y Seguridad — se referencia aquí porque en la FCT se aplica sobre un pipeline y una infraestructura reales, no simulados.

    1. Fundamentos de Seguridad en la Capa Cliente (Frontend Security)

    El navegador del usuario es un entorno de ejecución no controlado donde se procesan datos sensibles, tokens de sesión y lógica de negocio. Garantizar la seguridad en el desarrollo web en entorno cliente implica aplicar el principio de defensa en profundidad, neutralizando los vectores de ataque más habituales: Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF) e inyecciones de código.

    2. Prevención de Cross-Site Scripting (XSS)

    El ataque XSS consiste en la inyección de scripts maliciosos en la aplicación para ejecutarse en el navegador de la víctima, permitiendo el robo de cookies, tokens de acceso o la manipulación del DOM.

    2.1. Tipos de XSS y Mitigación en React

    Tipo de XSS Descripción Mecanismo de Prevención
    XSS Reflejado (Reflected) El script se envía en la URL/Petición y el servidor lo devuelve en la respuesta. Validar entradas e implementar cabeceras CSP.
    XSS Persistente (Stored) El script malicioso se almacena en la base de datos y se sirve a múltiples usuarios. Sanitizar en servidor y escapar al renderizar.
    XSS Basado en DOM (DOM-based) La vulnerabilidad está en el código JavaScript cliente al manipular innerHTML, eval() o location. Evitar asignaciones directas al DOM; usar React JSX / DOMPurify.

    2.2. Renderizado Seguro y dangerouslySetInnerHTML

    Por defecto, React previene XSS escapando automáticamente cualquier valor insertado en las expresiones JSX {variable}. Sin embargo, cuando se requiere renderizar código HTML rico provisto por los usuarios (ej. editores WYSIWYG), se debe utilizar la librería dompurify para limpiar el HTML antes de inyectarlo:

    import React from 'react';
import DOMPurify from 'dompurify';

interface ComentarioProps {
  contenidoHtmlBruto: string; // HTML potencialmente malicioso
}

export function ComentarioUsuario({ contenidoHtmlBruto }: ComentarioProps) {
  // Sanitización estricta eliminando etiquetas <script>, eventos inline, etc.
  const htmlSeguro = DOMPurify.sanitize(contenidoHtmlBruto, {
    ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p'],
    ALLOWED_ATTR: ['href', 'target'],
  });

  return (
    <div className="comentario-card">
      <h4>Comentario de la comunidad:</h4>
      {/* Inyección controlada de HTML previa sanitización */}
      <div
        dangerouslySetInnerHTML={{ __html: htmlSeguro }}
      />
    </div>
  );
}

    3. Politica de Seguridad de Contenido (Content Security Policy - CSP)

    CSP es una cabecera HTTP de seguridad (Content-Security-Policy) enviada por el servidor que permite definir qué orígenes de recursos (scripts, estilos, imágenes, conexiones HTTP) están autorizados a ejecutarse en el navegador.

    Content-Security-Policy: default-src 'self'; script-src 'self' [https://trustedscripts.example.com](https://trustedscripts.example.com); style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; connect-src 'self' [https://api.ejemplo.com](https://api.ejemplo.com);

    3.1. Directivas Principales de CSP

    • default-src 'self': Establece la regla por defecto: solo se permite cargar recursos del mismo origen (dominio y puerto).
    • script-src: Restringe las fuentes de archivos JavaScript. Deshabilitar 'unsafe-inline' bloquea la ejecución de scripts embebidos en el HTML, anulando la mayoría de ataques XSS.
    • connect-src: Limita los dominios a los que la aplicación cliente puede realizar peticiones asíncronas (fetch, axios, WebSockets).

    4. Almacenamiento Seguro de Sesiones y Cookies

    Guardar tokens de autenticación (ej. JWT) en localStorage o sessionStorage expone la sesión a cualquier vulnerabilidad XSS. La estrategia recomendada por OWASP es el uso de Cookies HttpOnly.

    flowchart LR
    subgraph Vulnerable ["Estrategia Vulnerable (LocalStorage)"]
        LS["localStorage.setItem('jwt', token)"] -->|Accesible por JS| XSSAttack["Ataque XSS roba el Token"]
    end

    subgraph Secure ["Estrategia Segura (HttpOnly Cookie)"]
        Cookie["Set-Cookie: token=...; HttpOnly; Secure; SameSite=Strict"] -->|Inaccesible para document.cookie| Protection["Protegido contra XSS y CSRF"]
    end

    Atributos Clave de Seguridad en Cookies

    • HttpOnly: Impide que el código JavaScript pueda leer la cookie mediante document.cookie (Inmunidad contra XSS).
    • Secure: Garantiza que la cookie solo se transmita en conexiones cifradas HTTPS.
    • SameSite=Strict / SameSite=Lax**: Restringe el envío de la cookie en peticiones de origen cruzado, previniendo ataques CSRF**.

    5. Pipelines CI/CD para Aplicaciones Web Cliente

    Un Pipeline de Integración y Despliegue Continuo (CI/CD) automatiza las fases de verificación de calidad del código, pruebas unitarias, auditoría de vulnerabilidades en dependencias y compilación antes del despliegue en producción.

    flowchart LR
    Push["1. Git Push / PR"] --> Lint["2. Linting & Formatting (ESLint/Prettier)"]
    Lint --> Audit["3. Security Audit (npm audit)"]
    Audit --> Test["4. Unit Tests (Vitest / Jest)"]
    Test --> Build["5. Build Producción (Vite)"]
    Build --> Deploy["6. Deploy (GitHub Pages / Vercel)"]

    5.1. Implementación Práctica: Pipeline con GitHub Actions

    A continuación se presenta un workflow de GitHub Actions completo (.github/workflows/ci-cd.yml) para verificar y desplegar una aplicación web cliente basada en React y Vite:

    name: CI/CD Pipeline - Web App Frontend

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  quality-and-security:
    name: Verificación, Seguridad y Build
    runs-on: ubuntu-latest

    steps:
      - name: 1. Clonar el repositorio
        uses: actions/checkout@v4

      - name: 2. Configurar entorno Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - name: 3. Instalar dependencias exactas
        run: npm ci

      - name: 4. Análisis estático (ESLint)
        run: npm run lint

      - name: 5. Auditoría de vulnerabilidades en dependencias
        run: npm audit --audit-level=high

      - name: 6. Ejecución de pruebas unitarias
        run: npm run test -- --run

      - name: 7. Compilación de producción (Vite Build)
        run: npm run build

      - name: 8. Subir artefactos de compilación (dist)
        uses: actions/upload-artifact@v4
        with:
          name: produccion-build
          path: dist/

  deploy:
    name: Despliegue Continuo
    needs: quality-and-security
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest

    steps:
      - name: Descargar artefacto compilado
        uses: actions/download-artifact@v4
        with:
          name: produccion-build
          path: dist/

      # Ejemplo de despliegue automatizado hacia GitHub Pages
      - name: Desplegar en GitHub Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./dist

    6. Cuadro Resumen de Buenas Prácticas de Seguridad y CI/CD

    Área Buena Práctica Riesgo Mitigado
    Sanitización Utilizar DOMPurify al renderizar HTML dinámico. Inyección de XSS persistente o basado en DOM.
    Cabeceras HTTP Configurar Content-Security-Policy estricta. Ejecución de scripts no autorizados e inyecciones.
    Sesiones Almacenar tokens en cookies HttpOnly + Secure + SameSite=Strict. Robo de credenciales mediante XSS y ataques CSRF.
    CI/CD Ejecutar npm audit y linters antes de cada fusión (merge). Despliegue de dependencias vulnerables o código defectuoso.
    Artefactos Compilar de forma limpia (npm ci y vite build) en entornos aislados. Alteraciones no autorizadas en los paquetes de producción.
